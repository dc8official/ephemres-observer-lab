Research scope & methodology

This lab measures how much a monitoring program's own busy-ness distorts the network latency it reports, and compares how Python (asyncio), Go and Rust cope. This page explains why and how it measures, then how to read the comparison table and the charts (Reading the comparison table, Reading the charts), how to run a valid test, and every control and metric.

The question

A monitor sends pings and reports how long each reply took. But between the moment a reply arrives at the computer and the moment the program reads it, the reply waits in a queue inside the operating system. If the program is busy (for example preparing a database write), the wait grows and the monitor reports a longer time than the network really had. That distortion is the observer effect.

The origin: While operating Ephemres (the parent monitoring platform) on deployed Linux machines, manual command-line ping tests from the terminal showed steady, low round-trip times, while the Ephemres application on the same machine reported a slight, regular RTT discrepancy and periodic tail-latency spikes. Ephemres was originally designed and tested inside a GNS3 simulated network environment on single-core (1 vCPU) Debian/Ubuntu machines, and as it grew, the most effective update specifically for improving ICMP accuracy was raising its database-write semaphore from 4 to 15. Before prematurely substituting Go or Rust into a working Python codebase, this lab was built to measure the observer effect on every packet across runtimes, CPU core modes, and semaphore sizes.

It answers five questions:

  1. How large is the distortion for a single-threaded asyncio monitor (Ephemres' 1-vCPU baseline design) under realistic database-write load?
  2. How does it change with the load: burst or staggered starts, endpoint count, semaphore size (testing the 4 → 15 tuning across 5, 15, 30, 50), and post-cycle CPU work?
  3. How do Go (goroutines) and Rust (tokio) compare to Python (asyncio) under the same load, pinned to one core and free to use all cores?
  4. What does Python gain, and what does it pay, when it moves the CPU work to worker processes (Python multi-core)?
  5. How do schedule design, hardware scaling, and language runtime each relate to the observer error measured here, for Ephemres and for monitoring platforms with a similar asynchronous probing architecture?

The clocks: how every packet checks itself

Instead of running a separate "control" ping at a different moment, every single reply is timestamped twice, by two clocks that both read the system clock (so they can be subtracted):

  • Clock A (kernel): the operating system records the arrival time and hands it over with the packet (a "control message" returned by recvmsg). It is fixed when the packet arrives, so it does not depend on what the program is doing. It is the lab's reference.
  • Clock B (observer): the program's own clock, read the instant its read call returns: clock_gettime_ns(CLOCK_REALTIME) in Python, time.Now() in Go, clock_gettime in Rust.
  • Optional hardware stamp: on a real network card the chip can stamp the frame itself. It is on a different clock, so it is never subtracted from A or B; it only lets you cross-check a row against tcpdump.

The ping's icmp_id and icmp_seq are echoed back by any target (RFC 792), which lets one socket serve hundreds of virtual endpoints pinging the same address: each endpoint gets its own identifier.

Kernel RTT is the reference, not a perfect "true" RTT: tx is read by the program just before it sends, so kernel RTT also contains the send call (a few µs; more if the program is paused right there). Observer lag is unaffected because tx cancels out; error % is slightly understated by the larger denominator.

Why simulated database work matters

A real asynchronous database write has two phases:

  1. Waiting for the database (network I/O). The program says "wake me when it answers" and the event loop goes on serving other work, including reading replies. This does not block.
  2. Preparing the write (CPU). Before sending anything the program computes statistics, evaluates state transitions, builds ORM objects and serialises SQL parameters. This is ordinary computation that keeps the thread busy: nothing else on that thread runs until it finishes.

Only phase 2 can delay reply reading, so that is what the lab simulates: a deterministic CPU spin of Simulated DB work milliseconds, limited to db_write_semaphore endpoints at a time, followed by a short sleep for phase 1. A spin instead of a real database removes disk and database variability, so any lag you see is scheduling contention inside the program, nothing else.

That is also why the engines differ: a single-threaded loop stops reading replies for the whole spin; Go and Rust with spare threads can keep reading while one thread spins; Python can move the spin to other processes, at the price of copying the data across the process boundary.

Two-tier architecture & the experiment matrix (engines × CPU core modes)

Two-tier system architecture & engine parity

To prevent the web dashboard from contaminating microsecond packet measurements, the lab splits execution across two isolated tiers (detailed in docs/03-architecture.md and docs/04-engines.md):

  • Tier 1 (Harness & Supervisory Server, server/app.py): Runs in its own process on unpinned cores, launches one isolated child probe process per run, consumes live NDJSON telemetry over stdout without blocking the probe, computes all statistics in one shared pipeline (server/analysis.py), and guarantees fail-safe process and NIC cleanup on exit.
  • Tier 2 (Probing Engine Runtimes: Python, Go, Rust): Each engine multiplexes up to 500 virtual endpoints (each identified by 0x1000 + i) over a single non-blocking 8 MiB raw ICMP socket (SOCK_RAW), extracts kernel SCM_TIMESTAMPING control messages (Clock A) via recvmsg, records user-space wake-up time (Clock B) immediately after, and runs a gated 10 ms scheduler canary alongside the semaphore-gated post-cycle CPU spin.

Why we test both Single-Core and Multi-Core modes

Every engine runs in two CPU core modes, so one comparison covers six combinations. The packets, schedule, simulated work and analysis are identical; only where the CPU work runs changes:

  • Single-Core (1-vCPU GNS3 baseline): Ephemres was originally designed and tested inside a GNS3 simulated network environment running on resource-constrained Debian/Ubuntu virtual machines with a single CPU core (1 vCPU). Pinning the probe process to a single core models that mandatory 1-vCPU operational constraint.
  • Multi-Core (scaling across modern hardware): Tests whether giving Go (GOMAXPROCS across all cores) and Rust (multi-threaded work-stealing tokio) spare OS threads, or offloading Python's CPU work to a ProcessPoolExecutor, eliminates event-loop and reader starvation when bursts collide.

Methodological note (Event-loop blocking vs. Garbage Collection): Literature on Python and Go tail latency highlights two distinct runtime overheads: (1) synchronous CPU work starving a cooperative event loop or thread scheduler, and (2) stop-the-world Garbage Collection pauses triggered by heap object allocations. Because this lab models the post-cycle ORM step as a deterministic 3.0 ms CPU spin rather than allocating thousands of temporary heap objects, it directly measures scheduler and event-loop contention.

How Python multi-core is measured

Python multi-core is monitored exactly like every other mode (both clocks on every packet, the canary, send lag, loss by cause), plus instruments specific to offloading:

  • Observer intrusion tests whether moving the 3 ms CPU spin off the event-loop thread lowers packet-reading delay, or whether baseline socket I/O and IPC serialisation keep intrusion bounded by the event loop itself.
  • ORM offload overhead (IPC + pool wait): for every cycle, the time the hand-over took beyond the work itself, i.e. copying (pickling) the data to a worker process, waiting for a free worker, and getting the result back. It is a row of the comparison table and a card in the drill-down; it is "n/a" in every other mode.
  • The pickling runs on helper threads inside the probe process, which take turns with the event loop for Python's interpreter lock (the GIL). That is why Python multi-core is not free: it can still delay reading replies, and the intrusion and canary show by how much.
  • ORM-work shading marks the offloaded jobs (hand-over to result). In this mode the stacks of high-lag dots should not line up with the shaded bands: if they still do, the hand-over itself is what delays the replies.
Pool size versus semaphore. The pool has one worker per CPU minus one (7 on an 8-CPU machine), while the Ephemres semaphore (expanded in production from 4 to 15 specifically to improve ICMP accuracy) lets 15 endpoints into the database step at once. The extra jobs queue for a worker, so with the Ephemres defaults the offload overhead under burst includes waiting for a worker, not only the copying. To measure the pure hand-over cost, run a variation with db_write_semaphore at or below the pool size (e.g. 7), and say so in the note.

The comparison is deliberately not perfectly symmetrical: in Go and Rust multi-core the CPU work shares memory with the reader, while Python's crosses a process boundary. That difference is part of what is being compared.

Reading the comparison table

Section 3 of the Lab tab puts the selected runs side by side: one column per run, one row per figure. Every figure is computed on the server from the per-packet timestamps, the same way for all three engines, with the warm-up cycle left out.

What a column is

  • One run, or with combine repeats on, one group of repeats (the runs of one batch with the same engine, CPU mode and role). A group's cell shows the median of its repeats with the lowest to highest repeat underneath. The median is the figure to quote; the range is how much simply repeating the run moves it.
  • The baseline is the column picked with ● in section 2 (by default the first test run, never an idle-floor run). With show × baseline, every other cell also shows its value as a multiple of the baseline's: ×2.0 means twice the baseline's value.
  • The thin bar under a value is its size relative to the largest value in that row, so you can scan a row without reading every number.

The marks: ▼ best and ▲ worst

  • Only rows where lower is better are marked, and only when the best and worst columns differ by at least the chosen threshold (10 % by default; 5-50 %, or never). Smaller gaps between single runs are usually noise.
  • With repeats there is a second condition: the best column's highest repeat must be below the worst column's lowest repeat. If the ranges overlap, the difference is within run-to-run noise and nothing is marked.
  • How much a mark means depends on the number of repeats: with 5 or more per column, non-overlapping ranges are evidence (p ≈ 0.008); with 3 they are a hint worth repeating (p = 0.10). See Running a valid test.
  • Idle-floor columns and the above-floor rows are never marked, and neither is error % of a run whose median kernel RTT is under 100 µs (shown as "n/m (RTT too small)"). Colours are never the only signal: every mark is also a ▼ or ▲.

Flags that change how far a number can be trusted

  • few samples: a percentile needs about 10 ÷ (1 − q) packets, i.e. about 200 for p95 and 1000 for p99. Below that the value is really one of the largest packets, not a percentile. The charts leave such points out.
  • Not like for like (the yellow banner): the selected runs differ in a setting other than the engine (endpoints, schedule, semaphore, ORM time, pings, interval, cycles, cycle length, timeout, NIC stamps or target). A difference in the results may then come from that setting. For a deliberate sweep of one setting use the sweep chart, which says which other settings also differ.
  • Scenario groups in section 2 collect the runs that asked the same question (same endpoints, schedule, semaphore, ORM time and target): ticking runs from one group keeps the comparison like for like.

The ⬇ Markdown and ⬇ CSV buttons export exactly this table, with each run's note, for reports.

Reading the charts

The table gives one number per figure; the charts show the shape behind it: how the waits are distributed, when they happened, who suffered, and whether a difference survives repeating the run. Every chart overlays the selected runs, each with a fixed colour and marker shape (● ▲ ■ ◆ …) shown in the legend strip above the charts. Charts that span microseconds to tens of milliseconds use a log axis, labelled at 1, 2 and 5 of each decade.

A reading order

  1. Check the inputs. The banner is clear (like for like), each run has enough packets (n in the legend), and loss is low.
  2. Headline: the table's intrusion p95 and primary error %, or Key metrics by run for a quick picture.
  3. Is it real? Spread across repeats: if the dots of two columns overlap, no difference is shown.
  4. Internal or external? Compare Intrusion at each percentile with Kernel RTT at each percentile.
  5. Where does it come from? Intrusion over time with the ORM-work shading, and the socket-queue rows of the table.
  6. Who pays? How concentrated is the damage.
  7. How does it grow with the load? The Sweep across a series that changes one setting.

Running a valid test

The full step-by-step protocol, with the host preparation, is Replicating the experiment below; these are the rules behind it.

  1. Check the target first with an ordinary ping: it should answer with no loss. The lab host's address must be in the same network as the target, otherwise the pings go to a gateway.
  2. Start from the Ephemres defaults (the form's starting values: 100 endpoints, 5 pings 8 s apart, starts spread over 60 s, 3 cycles). Change one setting at a time and write in the note what that change is testing. Use burst only to see the worst case, because a burst can overload the target and change the real RTT (the external effect).
  3. Check the host conditions shown with each run (CPU governor, deep sleep states, other load, NIC interrupts). Close other applications, and compare only runs taken under the same conditions.
  4. Leave NIC hardware timestamps off for any run you want to compare across engines: only Python can use them, and they change a setting on the network card.
  5. Compare like with like. Tick runs from the same scenario group; the page warns when selected runs differ in endpoints, schedule, semaphore, ORM time, pings, interval, cycles, cycle length, timeout, NIC hardware stamps or target.
  6. Repeat: 5 rounds for a claim. Which endpoints collide is not fixed, so one run is an anecdote. The run is the unit of replication, not the packet: packets of one run share the same stalls, so their count does not make a result more certain. If every repeat of one engine beats every repeat of another, the chance of that happening with no real difference is 10 % with 3 repeats each but under 1 % with 5. So use Repeat 5 to report a difference; 3 is a first look.
  7. Loopback (127.0.0.1) is only a functional check. The true RTT is a few microseconds, so error percentages look enormous.
  8. Quote the primary error %. The headline error is the total intrusion divided by the total kernel RTT (the share of all measured time that was error); the per-endpoint table uses the same definition. The per-packet median and mean are secondary: the mean can be dominated by one packet with a tiny RTT.
  9. Measure the idle floor of a setup (the "Measure idle floor" button: the same run with no ORM work) when you want to compare engines whose wake-up overhead differs; then tick "subtract idle floor" in the comparison. Raw figures stay the default.

Replicating the experiment

Everything needed to repeat the engine comparison on another machine. The full version, with commands, is docs/09-replication.md.

1. What you need

  • A Linux x86-64 machine (the prober host) with root, Python 3.10+, and optionally Go 1.22+ and Rust to build the other engines (./build_workers.sh).
  • A target on the same LAN segment that answers ping with 0 % loss. Nothing is installed or changed on it. Note its ordinary ping RTT.

2. Prepare the prober host

  • Close other applications; plug in the power (laptops throttle on battery).
  • For clean numbers: CPU governor performance, deep sleep states limited, the NIC's interrupts kept off the probe core (the last CPU). The dashboard records these host conditions with every run and warns about each one; report them with your results.

3. The protocol

  1. Start the dashboard (sudo .venv/bin/python -m server.app) and press Ephemres defaults.
  2. Enter the target. Leave NIC hardware timestamps off.
  3. Choose the CPU core mode to test. Under Batch engines, tick Python, Go and Rust; set Repeat to 5; tick Idle floor every round.
  4. Write the question in What is this run checking? (e.g. "Ephemres defaults, single core: which engine keeps intrusion lowest?") and press Start batch. Leave the machine alone until it finishes (the form shows how long).
  5. Repeat the whole batch with the other CPU core mode. Multi-Core covers Python multi-core too (its ORM work goes to worker processes), so the two batches together give all six engine × mode combinations. For a pure measurement of Python's hand-over cost, add a Multi-Core variation with db_write_semaphore at or below the pool size (CPUs − 1).
  6. Then each variation you study, changing ONE setting at a time from the Ephemres defaults.
  7. Every finished run is saved to test_results/ automatically (the header shows "auto-save on" and "0 unsaved"); saved runs reload after a restart.

4. Reading and reporting

What each row and chart means is in Reading the comparison table and Reading the charts.

  • Select the batch, keep combine repeats on. Compare medians and ranges; treat overlapping ranges as no difference shown (▼/▲ only appear when ranges are clear of each other; with fewer than 5 repeats treat them as hints).
  • Quote the primary error % (total lag ÷ total kernel RTT) and intrusion p95, with the number of repeats and packets (n).
  • For Python multi-core also quote the ORM offload overhead, and the semaphore and CPU count, since pool waiting is part of it.
  • Report the target RTT, the host conditions, the dashboard's settings (the Markdown export lists them), and whether the not-like-for-like banner was clear.
  • Share the result files: each run's .csv, _cycles.csv, .meta.json and its INDEX.md entry.

W. de Bruijn, "SO_TIMESTAMPING: Powering Fleetwide RPC Monitoring", Netdev 0x17 (2023) Demonstrates in Google's RPC fleet that user-space timing falsely blames the physical network for delays in the host's own software stack; poses the open question: "How much do measurements perturb the measured system?"
A. Pásztor and D. Veitch, "PC Based Precision Timing Without GPS", ACM SIGMETRICS 2002, 352-362 (and PAM 2001) Demonstrates that standard Unix active probers suffer from OS interrupt and scheduling noise, distorting software timestamps and jitter; establishes software timestamp inaccuracy in user-space probing.
T. Holterbach, C. Pelsser, R. Bush and L. Vanbever, "Quantifying Interference between Measurements on the RIPE Atlas Platform", IMC 2015, ACM, 437-443 The closest published evidence of a monitor distorting its own readings: on RIPE Atlas, a probe's own measurement load inflates the RTTs it reports (less on faster CPUs).
W. Li, D. Wu, R. K. C. Chang and R. K. P. Mok, "Toward Accurate Network Delay Measurement on Android Phones", IEEE Transactions on Mobile Computing 17(3), 717-732 (2018) Splits the RTT that measurement apps report into user-space and kernel-space inflation: the same split as Clock B − Clock A, applied to phones.
J. Sommers, P. Barford, N. Duffield and A. Ron, "Accurate and Efficient SLA Compliance Monitoring", ACM SIGCOMM 2007, 109-120 (and SIGCOMM 2005) Shows how probe schedules (bursts vs. Poisson/staggered) perturb network queues and distort SLA metrics: the theoretical foundation for separating internal from external observer effects.

Core literature: asynchronous runtimes, event-loop blocking and garbage collection

ReferenceWhy it matters here
J. Dean and L. A. Barroso, "The Tail at Scale", Communications of the ACM 56(2), 74-80 (2013) Foundational analysis of how background maintenance, garbage collection pauses, and shared-queue contention amplify p95/p99 tail latency in networked systems.
P. Galindo Salgado, "Time to take out the rubbish: garbage collector", PyCon US 2019, Python Software Foundation CPython core developer breakdown of Python's generational cyclic garbage collector (gc), explaining how cyclic traversal halts the interpreter and pauses the asyncio event loop.
C. Wu and M. Ni (Instagram Engineering), "Dismissing Python Garbage Collection at Instagram", Instagram Engineering Blog (2017) Production study showing how CPython cyclic GC pauses and copy-on-write page faults hurt tail latency and throughput in Python worker processes.
M. Nowack (Discord Engineering), "Why Discord is Switching from Go to Rust", Discord Engineering Blog (2020) Production comparison showing how Go's concurrent GC (forcing periodic mark/sweep scans every 2 minutes) caused latency spikes that Rust's zero-GC ownership model eliminated.
A. Clements, "Proposal: Non-cooperative goroutine preemption", Go Design Documents, Issue #24543 (2019) Explains Go's goroutine scheduler and preemption boundaries when tight CPU-bound loops compete with timer-woken goroutines.

Standards

ReferenceWhy it matters here
IETF RFC 2330, "Framework for IP Performance Metrics" (1998), §10.2, and RFC 7679, "A One-Way Delay Metric for IPPM" (2016), §3.7.2 The standards' distinction between wire time and host time, and the error between them: what Clock A and Clock B measure on every packet.
IETF RFC 3550 (RTP), section 6.4.1: smoothed inter-arrival jitter J ← J + (|D| − J) / 16 The jitter formula used. Any observer delay on a receive timestamp inflates |D| and contaminates the smoothed jitter of the packets that follow; the lab reports jitter on both the kernel and the observer clock.

Additional relevant literature for extended studies

ReferenceWhy it matters here
W. Heisenberg, "Über den anschaulichen Inhalt der quantentheoretischen Kinematik und Mechanik", Zeitschrift für Physik 43, 172-198 (1927) Conceptual analogy: observing more sharply disturbs more. In telemetry, frequent user-space observation injects interrupts and context switches into the packet pipeline.
B. Rossi and D. B. Hall, "Variation of the Rate of Decay of Mesotrons with Momentum", Physical Review 59(3), 223-228 (1941) Conceptual analogy: elapsed time depends on the frame of reference (wire time vs. kernel time vs. observer time).
J. Gait, "A Probe Effect in Concurrent Programs", Software: Practice and Experience 16(3), 225-233 (1986) Adding monitoring code to concurrent software changes its scheduling and event order: the original software "probe effect".
A. D. Malony, D. A. Reed and H. A. G. Wijshoff, "Performance Measurement Intrusion and Perturbation Analysis", IEEE Transactions on Parallel and Distributed Systems 3(4), 433-450 (1992) Models how much a monitor's own instrumentation perturbs the timing it measures, and how to subtract it: the formal precursor to subtracting an idle floor.
T. Mytkowicz, A. Diwan, M. Hauswirth and P. F. Sweeney, "Producing Wrong Data Without Doing Anything Obviously Wrong!", ASPLOS XIV, ACM, 265-276 (2009) Small differences in runtime and memory layout systematically bias benchmarks, which is why the lab runs identical packets, schedules and statistics in every engine.
T. Dreibholz, "High-Precision Round-Trip Time Measurements in the Internet with HiPerConTracer", SoftCOM 2023, IEEE, 1-7 A ping/traceroute tool that moved to kernel and hardware packet timestamps so that user-space scheduling no longer enters its RTTs; surveys the Linux timestamping options.
N. Zilberman, M. Grosvenor, D. A. Popescu, N. Manihatty-Bojan, G. Antichi, M. Wójcik and A. W. Moore, "Where Has My Time Gone?", PAM 2017, Springer LNCS, 201-214 Breaks host latency down from the application to the wire: host-side delay has many sources and must be measured.
A. Botta, A. Dainotti and A. Pescapé, "Do You Trust Your Software-Based Traffic Generator?", IEEE Communications Magazine 48(9), 158-165 (2010) Software tools do not send or time packets exactly as configured: the send-side counterpart of observer lag (compare send lag).
P. Emmerich, S. Gallenmüller, D. Raumer, F. Wohlfart and G. Carle, "MoonGen: A Scriptable High-Speed Packet Generator", IMC 2015, ACM, 275-287 Uses NIC hardware timestamps for sub-microsecond latency measurement because software timestamps are not precise enough.
V. Paxson, "On Calibrating Measurements of Packet Transit Times", ACM SIGMETRICS 1998, 11-21 Clock adjustments and skew corrupt delay measurements even under NTP: the background to the clock-slew threat.

What this lab adds. The work above shows that measuring hosts add error and how to timestamp around it. As far as this project's literature search went, none of it captures SO_TIMESTAMPING and application time on every single packet simultaneously to isolate user-space delay, measures how much the monitor's own post-probe database work delays reading replies and contaminates in-flight measurements of other endpoints, compares concurrency runtimes (asyncio, Go goroutines, tokio tasks; one core and all cores) under identical loads, quantifies Python's multi-core process-offload tax, or separates loss caused by the observer from network loss.

Full project documentation, including methodology details and the Linux timestamping interface, is in the docs/ folder.
